FrAIm - Known Bugs
==================

Bugs found while working on the code, kept here so they can be fixed later.

How to use this file
- Add new bugs at the end, with the next free number (one more than the last entry's). Never reuse a number.
- When a bug is fixed, set its Status to "Fixed (<date>, <commit>)" and leave the entry in place.
- Locations name the class and method. Line numbers are only a hint, as they change when the code is edited.

Entry fields
- Status:   Open / Fixed / Won't fix
- Severity: High (wrong results, crash, data loss) / Medium (feature doesn't work as intended) /
            Low (usability or cosmetic issue, with a workaround)
- Found:    date, and what was being worked on at the time

BUG-001  Help buttons do nothing on the first click
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Low (usability: clicking a second time works)
Found:    2026-11-07, while adding Javadoc to DataAwareController

Where (all 9 "Help" buttons have the same bug):
- DataAwareController:            onClickToolTip(), onClickToolTipPN(), onClickToolTipPlan()
- DataAgnosticController:         onClickToolTip(), onClickToolTipPN(), onClickToolTipRunPlan(), onClickToolTipPlan()
                                  (the Data-Agnostic page is currently disabled, see the note on BUG-009)
- ProcessFrameOverviewController: onClickToolTip(), onClickToolTipPN()

Steps to reproduce:
1. Start FrAIm and open the Data-Aware page (or Data-Agnostic, or Process Frame Overview).
2. Click any "Help" button once.

Expected: The help popup opens below the button.
Actual:   Nothing happens. The popup only opens on the second click.

Cause:
The FXML wires each button to its onClickToolTip...() method (onAction="#onClickToolTip..."). That
method only builds the popup and then replaces the button's action with button.setOnAction(...),
which toggles the popup. It never shows the popup itself, so the first click is spent setting the
button up. Each later click works, but the first click on every page does nothing.

Suggested fix:
Build each popup once, either in initialize() or the first time it's needed, and show/hide it
directly in the FXML handler instead of calling setOnAction(). The nine methods are near-identical,
so a shared helper (e.g. in AbstractController) taking the button and the popup content would remove
the duplication.

To check while fixing (not verified):
The popups use setAutoHide(true). Clicking the Help button while its popup is open may hide the popup
on mouse press and immediately reopen it on the button's action. If so, a second click doesn't close
the popup. The attribute popup of the Prefix list's events works the same way (EventCell.onClickExtend(),
noted 2026-11-07), so check it as well.
I checked whether the popup closes on the second mouse press, and the behaviour is as expected, i.e. the popup closes and stays close.
Therefore, this is not a bug, and there is no need to change it.

BUG-002  "mvn javadoc:javadoc" fails because of malformed Javadoc comments
---------------------------------------------------------------------------------------------------
Status:   Fixed (2026-11-07, not committed yet) - "mvn javadoc:javadoc" now ends in BUILD SUCCESS
Severity: Low (build/documentation: the HTML docs are still written to target/reports/apidocs)
Found:    2026-11-07, after adding the maven-javadoc-plugin to pom.xml

Where (lines as of 2026-11-07):
- EnhspPlanParser.java:           class comment (lines 29-33), constructor @param tags (lines 114-116),
                                  parse() @param prefixEvents (line 182) - 17 errors
- RunEnhspTask.java:              class comment (line 24) - 3 errors
- GenerateDataAwarePDDLTask.java: class comment (line 15) - 1 error

Steps to reproduce:
1. Run "mvn javadoc:javadoc" in the project root.

Expected: BUILD SUCCESS.
Actual:   BUILD FAILURE with 21 errors, e.g. "element not closed: i" and "unknown tag: cost".

Cause:
The comments use placeholders such as problem<i>.pddl, <cost> and "<model file>|<constraint name>".
Javadoc reads them as HTML tags (<i> is italics), and the plugin's doclint setting
(<doclint>all,-missing</doclint>) treats malformed HTML as an error.

Fix:
The placeholders are wrapped in {@code ...}, e.g. {@code problem<i>.pddl}. The two tables in the class comment of
EnhspPlanParser are in <pre> blocks, so they keep their layout in the HTML docs. Only comments were changed.
For new Javadoc: write placeholders in {@code ...} or as &lt;i&gt;. A bare "->" is fine (JDK 21 doesn't flag it).

BUG-004  Data-Aware: model labels after "Run Planner" have a trailing "+" and are never cleared
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Low (cosmetic)
Found:    2026-11-07, while adding Javadoc to DataAwareController

Where: DataAwareController.onClickPlanner(), the end of the method (selectedDecl / selectedPN labels,
       around lines 1104-1213)

Steps to reproduce:
1. On the Data-Aware page, select one Declare model (e.g. "declA") and no Petri net.
2. Click "Run Planner".

Expected: The label names the planned model(s), e.g. "declA", or "declA + declB" for two models.
Actual:
- The label reads "declA+": every model name is followed by a "+", including the last one.
- The Petri net label is made visible even when no Petri net is selected (its text is empty).
- The labels are set as soon as Run Planner is clicked, even if planning then fails or is cancelled.
- The labels stay as they are after Reset, after switching prefixes, and after changing which models
  are selected. They're only hidden when the page is first opened (initialize()).

Cause:
The names are built with name + "+" in a loop. The labels are made visible unconditionally, inside
try/catch blocks that ignore exceptions ("// TODO: handle exception").

Suggested fix:
Build the text with String.join(" + ", names), only show a label when it has models to name, and
update or hide the labels together with the plan (e.g. in loadPlans() and in onClickPrefix()). The
empty try/catch blocks can be removed.

BUG-008  Data-Aware: files from a previous run that can't be deleted are silently reused
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Medium (wrong results without notice), but unlikely
Found:    2026-11-07, while adding Javadoc to GenerateDataAwarePDDLTask

Where:
- GenerateDataAwarePDDLTask.call() (around lines 128-133) and deleteFiles() (around line 187)
- EnhspPlanParser constructor (around line 169), which reads every activity mapping file it finds
- RunEnhspTask.call() (around line 138), which deletes the old plans the same way (added 2026-11-07,
  while adding Javadoc to RunEnhspTask)

Steps to reproduce:
1. Run the planner on the Data-Aware page once.
2. Make output/variable_values.txt (or an output/activityMapping_*.txt file) impossible to delete,
   e.g. set it to read-only, or open it in a program that locks it.
3. Change the selected models or the prefixes, and run the planner again.

Expected: The run fails with a message that a file from the previous run couldn't be deleted.
Actual:   The failed deletion is ignored (the result of File.delete() isn't checked). The generator
          only creates the variable files if they don't exist yet, so it keeps the old encodings,
          and the plans' attribute values are decoded with those. A leftover activity mapping file of
          a model that's no longer selected is still read by EnhspPlanParser, and may map an
          encoding to the wrong activity. Likewise, if output/plans/plan<i>.txt can't be deleted and
          problem i isn't generated this time, DataAwareController.loadPlans() loads that old plan for
          prefix i, while the message says that no plan was found for it. (Not verified by running it.)

Suggested fix:
Delete with Files.deleteIfExists(...), which throws if the file can't be deleted, and let the task
fail with that message.

BUG-009  Data-Agnostic: Cancel doesn't stop PDDL generation, and later reports it as failed
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Medium (Cancel doesn't work as intended)
Note:     The Data-Agnostic page is currently disabled: PageType.DATA_AGNOSTIC is commented out
          (util/PageType.java), so the page can't be opened. This only matters if it is enabled again.
          (Noticed 2026-11-07, while adding Javadoc to ProcessFrameOverviewController.)
Found:    2026-11-07, while adding Javadoc to GeneratePDDLTask

Where:
- GeneratePDDLTask.call() (around lines 81 and 109)
- DataAgnosticController.onClickPlanner(), the progress layer's cancel handler (around line 396), and
  the task's onFailed handler (around line 477)

Steps to reproduce:
1. On the Data-Agnostic page, click "Run Planner".
2. Click "Cancel" on the progress layer while the PDDL problem is still being generated.

Expected: The Framed Autonomy Tool is stopped, and nothing more happens.
Actual (from reading the code, not verified by running it):
- The tool keeps running until it's done.
- Once it's done, the error "Generating PDDL failed" appears, although the user cancelled.
- That task's failure handler then also resets the plan state (setPlanPresent(false),
  updatePrefix(null)). If the user has already started another planner run, it runs in the middle of it.

Cause:
Cancel only calls executorService.shutdownNow(), which interrupts the task's thread; the task itself
isn't cancelled (see the TODO there). GeneratePDDLTask is then blocked in reader.read() on the tool's
output, which an interrupt doesn't wake up, and it never checks isCancelled(). When it gets to
process.waitFor(), the thread is still marked as interrupted, so waitFor() throws
InterruptedException and the task fails instead of being cancelled. The tool's process is never
destroyed, unlike in RunnerUtils.runProcess(), which destroys it when interrupted.

Suggested fix:
In the cancel handler, call cancel(true) on the running task, as the Data-Aware page does, instead of
shutting down the executor. In GeneratePDDLTask.call(), destroy the process if the task ends while
it's still running (e.g. in a finally block: if (process.isAlive()) process.destroyForcibly()).
Destroying the process also makes the blocked read() return.

BUG-010  Data-Aware: the planner refuses to run unless the PDDL domains were copied into dependencies/
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Medium (on a fresh setup the planner can't run; workaround: copy the domains by hand)
Found:    2026-11-07, while adding Javadoc to RunEnhspTask

Where:
- DataAwareController.onClickPlanner() (around lines 1122-1126), the check before planning
- RunEnhspTask.findDomain() (around line 200), which has a fallback the check never lets it reach

Steps to reproduce:
1. Set up FrAIm as described under "Building with Maven" in README.md (which says "nothing has to be
   installed by hand"), so dependencies/ only holds enhsp.jar and the generator's jar.
2. On the Data-Aware page, select a Declare model and click "Run Planner".

Expected: The planner runs with the domain that comes with the generator.
Actual:   "The PDDL domain for the recovery strategy "Reset" was not found: ...\dependencies\
          domain_framed_autonomy_process_reset_time_costs.pddl", and nothing is planned. (Not verified
          by running it: the machine this was found on has the domains in dependencies/, copied by hand.)

Cause:
dependencies/ isn't in git, and "mvn package" only copies enhsp.jar and the generator's jar into it.
RunEnhspTask.findDomain() would extract the strategy's domain from the pddl_gen jar FrAIm depends on;
the jar does contain all of them (domains/*.pddl). But onClickPlanner() checks for the domain in
dependencies/ first and stops if it isn't there.

Suggested fix:
Let the check accept the domain from the jar as well, e.g. a RunEnhspTask method that tells whether
findDomain() would find one, or drop the check and let RunEnhspTask report a missing domain. Also
README.md: the list of domain files under "Multi-Perspective" is empty.

BUG-011  Data-Aware: the Discard and Skip domains in dependencies/ differ from the generator's
---------------------------------------------------------------------------------------------------
Status:   Open - needs a decision on which version is correct
Severity: Medium (plans and plan costs may differ between machines for Discard and Skip)
Found:    2026-11-07, while adding Javadoc to RunEnhspTask

Where:
- dependencies/domain_framed_autonomy_process_discard_time_costs.pddl (line 685) and
  dependencies/domain_framed_autonomy_process_skip_time_costs.pddl (line 654), copied there by hand
- domains/ inside the pddl_gen jar (data-framed-autonomy), the same two files
- RunEnhspTask.findDomain(), which prefers the copy in dependencies/

What differs (the other three domains are identical):
  dependencies/:  (increase (total_cost) (/(violation_cost ?c) (waiting_cost)))
  pddl_gen jar:   (increase (total_cost) (violation_cost ?c))

So with the dependencies/ copies, a violation costs violation_cost / waiting_cost; with the jar's,
it costs violation_cost. Which one is used depends on whether a machine has the copies in
dependencies/. If BUG-010 is fixed, machines without them get the jar's version.

Steps to reproduce:
1. Compare the two files in dependencies/ with domains/ in
   ~/.m2/repository/org/example/pddl_gen/1.0-SNAPSHOT/pddl_gen-1.0-SNAPSHOT.jar.

Expected: One version of each domain.
Actual:   Two versions, so the plans found may differ for the same input. The plan cost's breakdown
          (DataAwareController.describePlanCost(), EnhspPlanParser) may only add up with one of them;
          not checked which.

Suggested fix:
Decide which version is correct, put it into data-framed-autonomy (so the jar and the generator
agree), and remove the hand-copied domains from dependencies/, or have "mvn package" copy them there
from the jar so they can't drift apart.

BUG-017  Data-Aware: the timestamp field accepts impossible dates and silently changes them
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Medium (the planner gets a different time than the one shown), but only for impossible dates
Found:    2026-11-07, while adding Javadoc to EventCell

Where:
- EventCell.parseTimestamp() and TIMESTAMP_FORMATTER (around lines 61 and 355)
- DataAwareController.parseTimestamp() and XES_TIMESTAMP_FORMATTER (around lines 368 and 1691),
  which read the stored timestamp the same way when exporting the prefixes

Steps to reproduce:
1. On the Data-Aware page, select a Declare model with a time condition, so prefix events get a
   timestamp field.
2. Open a prefix event's attribute popup and confirm the timestamp 2023-02-30T10:00:00.

Expected: Rejected, like other invalid timestamps ("Not a valid timestamp"), as the comment on
          parseTimestamp() said it would be.
Actual:   Accepted. The field keeps showing 2023-02-30T10:00:00, since the text is stored as typed, but
          it's read, checked against the neighbouring events and exported to the planner as
          2023-02-28T10:00. Checked with the same formatter: 2023-02-30 and 2023-02-31 become
          2023-02-28, 2023-04-31 becomes 2023-04-30, and 24:00:00 becomes 00:00 of the next day.
          2023-02-32 and month 13 are rejected.

Cause:
DateTimeFormatter.ofPattern(...) resolves in SMART mode, which moves a day-of-month that's too large
for its month to the month's last day instead of failing.

Suggested fix:
Validate with DateTimeFormatter.ofPattern("uuuu-MM-dd'T'HH:mm:ss").withResolverStyle(ResolverStyle.STRICT)
(STRICT needs "uuuu" instead of "yyyy").

BUG-018  Prefix/Continuation lists: a normal event may be shown in italics like the trace start/end
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Low (cosmetic)
Found:    2026-11-07, while adding Javadoc to EventCell

Where: EventCell.updateItem() (around lines 148-158)

Steps to reproduce (not verified by running it):
1. On the Data-Aware page, build a prefix (or get a plan) long enough that the list needs scrolling.
2. Jump between the trace start and the trace end (e.g. with the timeline slider), so the same list
   cell shows the start, then the end, then a normal event.

Expected: Only "-trace start-" and "-trace end-" are in italics.
Actual:   That normal event is in italics as well.

Cause:
Each time a cell shows the start or end, it adds the style class "event-title__artificial" (italic, see
main.css) again, without checking whether the cell already has it. For a normal event, remove() only
takes out one copy, so a cell that has shown the start or end twice since it was created keeps one.
(ListView.refresh() creates new cells, which hides this most of the time.)

Suggested fix:
Only add the class if it isn't there yet, or use a PseudoClass (pseudoClassStateChanged(...)), which
can't be added twice.

BUG-026  Declare replay: constraints whose activation and target are the same activity are evaluated
         wrongly
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Low (such constraints are unusual)
Found:    2026-11-07, while adding Javadoc to DeclareConstraint

Where: DeclareConstraint.getAutomataLabel(...) (around lines 178 and 195)

Steps to reproduce (checked by replaying with DeclareModel.updateMonitoringStates()):
1. Load a Declare model with "Co-Existence[ActivityA, ActivityA]" and "Not Response[ActivityA, ActivityA]".
2. Replay the trace <ActivityA, ActivityA>.

Expected: Co-Existence[A, A] is satisfied (it always is), and Not Response[A, A] is violated (the second
          A follows the first).
Actual:   Co-Existence[A, A] ends violated, and Not Response[A, A] ends satisfied.

Cause:
Each event is fed to the constraint's automaton as one letter: "A" for the activation, "B" for the
target, "Z" for anything else. When both are the same activity, every occurrence is checked against
the activation first and becomes "A" only, so the automaton never sees a "B".

Suggested fix:
For such constraints, build the automaton from the template's formula with B replaced by A (so the one
letter stands for both), or handle these templates separately.

BUG-027  Petri net replay: an event isn't flagged as a violation if its name is part of an enabled
         transition's name
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Medium (violations go unnoticed, in the viewer and in the plan cost)
Found:    2026-11-07, while adding Javadoc to PnModel

Where: PnModel.updateMonitoringStates() (around lines 162-179). The code has a TODO about it.

Steps to reproduce (checked by replaying with PnModel.updateMonitoringStates() on the example net
bpm-demo-tool/examples/a29g9AND.pnml):
1. Replay the trace <ActivityA, ActivityZ, n64, ActivityA> on that net. After the third event, only
   ActivityAC and ActivityAB are enabled.

Expected: The second ActivityA is a violation: the Petri net viewer shows it in red, and isViolated()
          is true.
Actual:   It isn't recorded as a violation (isViolated() is false), and it isn't fired either. The
          console shows "IllegalTransitionException: Cannot execute transition activitya in state ...".

Cause:
Whether a transition is enabled is checked with
currentlyEnabledTransitions.toString().toLowerCase().contains(act), a text search in the list of enabled

then fails, and the exception is only printed. This affects any net with a transition name that's part
of another one's, e.g. ActivityA next to ActivityAB.

Knock-on effect: for Discard plans, DataAwareController.getReplayedViolationCost() takes a net's
violation cost from isViolated(), so such a violation also goes missing from the plan cost breakdown.

Suggested fix:
Check whether the transition itself is among the enabled ones, e.g.
currentlyEnabledTransitions.contains(getTransitionViaLabel(..., act)).

BUG-028  Petri net replay: silent transitions are never fired, so fitting traces can show violations
---------------------------------------------------------------------------------------------------
Status:   Open
Severity: Medium for nets with silent (invisible) transitions, none otherwise
Found:    2026-11-07, while adding Javadoc to PnModel

Where: PnModel.updateMonitoringStates() (around lines 145-179)

What happens (from reading the code; the example nets in bpm-demo-tool have no silent transitions, so
it wasn't checked by running it):
The replay only ever fires the transition named by the current event. A silent transition (a "tau",
e.g. for an XOR split, a loop or a skip, as process discovery tools often create) is never fired,
because no event names it. In a net where a visible transition only becomes enabled after a silent one,
an event of that transition is recorded as a violation, even though the trace fits the net. The viewer
shows it in red, and the net counts as violated (see BUG-027's knock-on effect).

Suggested fix:
Before giving up on an event whose transition isn't enabled, look for a sequence of silent
transitions that enables it (e.g. a short breadth-first search over silent transitions only) and fire
those first.
